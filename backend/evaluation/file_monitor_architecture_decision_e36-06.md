# FileNest 第 36 课：V1 file monitor 接入决策（E36-06）

## 决策

当前 FileNest V2 **暂不接入 V1 file monitor**，保留显式扫描和索引同步路径；待明确的 V2 产品需求与事件流证据出现后再重新评估。

这里的“暂不接入”是本课的工程决策，不是否定旧版桌面产品的持续监控方向，也不把旧版实现自动视为 V2 后端能力。

## 证据范围

- `backend/evaluation/long_task_http_boundary_e36-01.md` 已明确：V1 file monitor 不是已证实的 HTTP 长任务，是否接入必须由独立产品需要和资源证据决定。
- 当前 V2 后端的真实长任务证据是大规模工作区扫描和大规模文档索引；文件搜索仍为毫秒级。现有后端入口是显式扫描/同步，没有 monitor 事件入口。
- 当前 V2 已建立 Job、Attempt、进度、取消、重试、SQLite 持久化和单进程恢复基线，但没有把文件系统事件映射为 Job 的语义。
- 根目录 `README.md` 与 `core/file_monitor.py` 属于旧版桌面程序。旧版 monitor 监听直接子文件的创建/修改事件，使用内存队列和 3 秒防抖；它没有 V2 的路径授权、Job/Attempt、持久化、重启恢复或索引同步边界，因此不能直接移植为 V2 实现。

## 为什么现在不接入

1. 旧版 README 说明了持续监控的产品方向，但没有证明 V2 当前版本已经承诺实时建议、监控目录范围或后台生命周期。
2. 监控会引入连续事件流、写入完成防抖、重复事件合并、重命名/移动/删除语义、路径授权、Watcher 健康检查和重启恢复；当前没有这些行为的 V2 合同或验收标准。
3. E35/E36 的实测瓶颈支持显式大规模扫描和文档索引后台化，不支持为了监控而扩大任务系统、事件队列或资源模型。
4. 直接复用旧版 monitor 会绕过 V2 的文件系统安全边界，也无法说明事件是否已经稳定、文件是否仍在写入或索引是否应被重新计算。

## 重新评估条件

同时满足以下条件后，再单独设计 V1 monitor 接入：

- V2 产品需求明确要求对选定目录提供实时新文件建议；
- 监控目录、工作区归属、路径授权和用户启停语义已经确定；
- 通过代表性工作负载测量事件数量、重复率、写入抖动、CPU/内存和积压风险；
- 明确创建、修改、重命名、移动、删除以及临时文件的处理规则；
- 明确事件合并到 Job 的幂等键、取消、重试、Watcher 重启和失败告警语义。

## 当前影响

- 用户仍可通过显式扫描获得工作区文件索引；已确认的长任务继续使用现有单进程 Job 基线。
- 本次不新增运行时代码、测试、依赖或 HTTP 接口，也不修改旧版 `core/file_monitor.py`。
- `E36-06` 完成的是“根据当前真实需要作出不接入决定”，不是实现 monitor。
