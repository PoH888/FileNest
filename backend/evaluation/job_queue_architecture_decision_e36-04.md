# FileNest 第 36 课：任务队列架构决定（E36-04）

## 决定

1. **当前不引入 Redis。**
2. **当前不引入 Celery。**
3. 继续保留 E36-03 的标准库单进程、单 worker、内存 Job Runner 作为最小基线。
4. 先用 E36-05 验证重复投递、worker 中断和服务重启，再由观察到的失败决定是否增加 SQLite 持久化或重新评估外部队列。

这是一项基于当前产品规模和证据的可撤销决定，不是永久禁止 Redis/Celery。

## 决定所依据的证据

- E36-01 已确认 10,000 文件扫描中位数为 14,742.750 ms，8,000 文档索引中位数为 26,201.679 ms；这些数据证明部分行动需要脱离同步 HTTP 请求执行。
- 长任务耗时本身不等于分布式队列瓶颈。当前没有队列等待时间、积压长度、并发 worker 吞吐、多进程竞争或多主机调度测量。
- E36-03 已使用 `ThreadPoolExecutor(max_workers=1)` 建立单进程基线，并验证异步执行、进度回报、协作式取消和同进程重复提交防重。
- 当前 FileNest 是本地单用户应用，数据库仍为 SQLite；没有远程多用户部署或独立任务集群需求。
- `requirements.txt` 当前没有 Redis 或 Celery 依赖，项目也没有相应服务配置和运维边界。

## Redis/Celery 当前不能直接解决的问题

- 不能让扫描、文档解析或 ORM 持久化本身自动变快；这些仍是 E36-01 已测到的主要耗时。
- 不能替代 Job、Attempt、进度、取消和重试状态语义；这些必须由 FileNest 自己保持一致。
- 不能替代路径授权、文件变化校验、审批和安全执行边界。
- 不能仅凭安装依赖就证明服务重启恢复、幂等消费或重复投递正确。

## 当前已知限制

- Job 状态和幂等索引只存在当前进程，服务重启后会丢失。
- 单 worker 会串行处理任务；尚未测量真实队列等待时间和积压。
- 尚未把 Runner 接入 HTTP、工作区扫描或文档索引。
- 尚未验证进程退出时运行中 Attempt 的恢复语义。

这些限制是 E36-05 的验证输入，不是现在引入 Redis/Celery 的充分证据。

## 重新评估条件

出现以下任一可复现证据时，重新评估 Redis/Celery 或其他外部队列：

- 代表性任务积压使以后明确制定的队列等待目标持续失败，且单进程优化无法满足；
- 产品需要多个进程或多台主机领取任务，并需要独立于 Web 进程的 worker 生命周期；
- SQLite 持久化基线无法可靠实现所需的任务领取、重复投递防重或中断恢复；
- 需要成熟的任务路由、定时调度、限流或跨 worker 重试能力，并有对应产品需求；
- 外部队列服务的部署、监控、备份和故障处理成本已经有明确责任边界。

## 当前明确不做

- 不修改 `requirements.txt`；
- 不安装、启动或配置 Redis；
- 不创建 Celery app、task 或 worker；
- 不修改 Job Runner、HTTP API 或数据库 schema；
- 不接入 V1 file monitor；
- 不新增等价测试或扩大测试矩阵。

## 复用验证

```powershell
.\.venv\Scripts\python.exe -m pytest `
  tests\test_job_system.py `
  tests\test_job_runner.py `
  -q -p no:cacheprovider
```

该命令只验证当前 Job 状态机和单进程基线，不宣称已经具备进程重启恢复或分布式执行能力。
